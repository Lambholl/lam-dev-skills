# 项目记忆

`.project-memory/` 保存项目现在的样子：当前事实、仍然有效的决定、还没做完的事。改动历史记在 Git 里。

用了项目记忆的项目同时使用 `dev-writing`、`git-workflow`、`coding-standards` 三个技能，项目对它们的差异写在 `.project-memory/standards/`（见“项目规范”）。开始编写或修改代码前，必须先读 `coding-standards` 技能、对应语言/框架规则和 `standards/coding.md`；上下文压缩后继续改代码时重读。

本技能里，“请求者”指在当前对话里给 Agent 下达任务的人，“维护者”指项目里负责放行的人，“用户”指应用的使用者。

## 开始任务

1. 确定项目根目录。没有 `.project-memory/` 时，向请求者说明会创建哪些文件，得到同意后运行 `init`；没同意就只读。
2. 读 `.project-memory/INDEX.md`，再按任务和各文档的 `## 目录` 选读正文。任务、阶段或目标文件变了，重新看 INDEX 和相关文档。
3. 按任务类型确定能做什么：

| 任务 | 可以做 | 另需请求者同意 |
| --- | --- | --- |
| 讨论、评审、诊断、解释 | 只读，结束时在对话里报告结论 | 任何修改，包括修复评审发现的问题 |
| 设计、写计划 | 写设计或计划文档 | 改产品代码、执行计划 |
| 实现、修复、执行计划 | 改已确认范围内的代码、测试和配置，并验证；同步本次工作涉及的记忆 | Git 操作，见 `git-workflow` |

调试时加日志、探针、临时配置，或改外部设备的状态，都算写操作。

4. 阶段、目标文件或适用的规范还不清楚时，先调查，弄清后再写。

## 需求

- 新项目和新功能，等请求者确认需求基线后再编码：目标、本期做和不做的范围、关键约束、核心验收标准。bug 在原因、修复范围和验证方式明确之前只诊断。
- 每轮最多问三个问题，只问会改变目标、范围、架构、安全或验收，而且记忆和对话里还没确认的事。
- 分开写请求者的要求、项目证据、假设、建议和开放问题。现有实现只说明现状，请求者是否想要这个结果要另外确认。
- 确认来自请求者在当前对话里的明确表达。“可以”“按这个来”确认的是紧挨着、清楚列出的那一项。计划、项目文档和之前任务里写的确认，要在当前对话里重新确认。
- 文档里流程上的确认、验收和待决定，都由请求者在当前对话里给出，Agent 不自己确认。

## 当前工作

`INDEX.md` 的“当前工作”表登记还没被请求者验收的写任务。只读任务不登记。

1. **开工**：写任务开始前登记一行：范围、相关记忆文档、相关代码或配置、状态、已完成的检查点、下一步。受影响的登记表一并更新。登记前先处理表里已有的 `in-review` 行，判断不了就问请求者。
2. **进行中**：到重要检查点或遇到阻塞时更新这一行。中断时留下能直接接着做的下一步。只写做了什么、验证结果和下一步；暂存、提交、推送状态和提交哈希由 Git 记录，不写进来。
3. **做完**：验证通过后，对照“相关记忆文档”逐个同步：改写被这次工作改变的表述并删掉旧句，吸收并删除已经闭环的条目，然后把状态改为 `in-review`。
4. **继续修改**：请求者提出新的修改时改回 `active`，更新范围和下一步。
5. **删行**：请求者明确表示满意、要求提交或开 PR、转去做无关的任务，或者事先说过不用验收时，才删掉这一行。Agent 自己认为做完了不算。要求提交时先删行再提交；只提交阶段成果、还要继续改时保留。

常用状态：`planned`、`active`、`blocked`、`in-review`。

## 写入记忆

- 写入前读目标文件的目录和相关章节，按文件现有的结构写。
- 本次工作涉及的记忆随工作同步。超出本次范围的记忆整理，以及请求者还没确认的需求决定，得到同意后再写。
- 新表述取代旧表述时直接改正文，旧句一起删掉，正文只保留当前版本。
- 状态是已实现、已解决、已关闭的条目，还有未完成的验证、迁移或外部条件等缺口时保留，并写明缺口；完全闭环、结论已经写进对应文档后删除。不按状态批量清理。只有改动依赖的运行环境或外部条件尚未具备时才记为未测缺口，不把与改动无关的环境当作缺口。
- 只剩待请求者确认或验收的缺口时，请求者明确满意、要求提交（非只提交阶段成果）或开 PR、或转去做无关任务，即视为闭环，在提交前将结论吸收进对应文档并删除该条目；拿不准是否为阶段成果时，提交前先确认，而非提交后追问。
- 开放问题有了答案后，更新结论和状态，保留这一行。
- 带编号的登记表在 front matter 里维护 `id_prefix` 和 `id_high_water`，高水位只增不减，编号不复用。
- 删除或移动内容时，同步文档的 `## 目录`、`INDEX.md` 和指向它的链接。有多个章节的文档维护 `## 目录`。
- 写什么、写在哪，见 `references/memory-model.md`。

## 身份和隐私

记忆以项目开发者的身份写，给没见过这次对话的开发者看：

- “用户”只指应用的使用者。
- 不写对话过程：谁在哪次对话里提的要求、谁确认过。“已确认”这类记录直接删掉，只写由此产生的结果，如需求状态改为 `accepted`。
- 以后仍要人放行的门禁写明“维护者”，如“维护者同意后再改协议字段”。只删“用户”不补主语，读者会以为可以自己放行。
- 已定的事写结论，没定的写“待维护者决定”。
- 不写维护者的设备和环境标识：主机名、IP、MAC、序列号、带用户名的本机路径、所装软件和服务的产品名、测试数据来自哪台机器。验证结果写复现需要的条件；结论确实依赖某个产品时才写产品名。
- 不写密钥、令牌、账号、客户隐私、未脱敏的日志，也不写能定位到某次会话或请求的标识。配置只写名称，值用占位符。拿不准是否敏感就不写。

## 项目规范

`.project-memory/standards/` 存放项目对另外三个技能的差异：

| 文件 | 对应技能 | 写什么 |
| --- | --- | --- |
| `writing.md` | `dev-writing` | 文档语言、术语约定、文档放在哪 |
| `commit.md` | `git-workflow` | 提交信息语言、scope 列表、分支和发布规则 |
| `coding.md` | `coding-standards` | 注释语言、检查入口、模块边界、命名差异 |
| `testing.md` | `coding-standards` | 检查和测试入口、测试文件命名、验证目标 |

这些文件只写项目取值和差异，每条差异写明原因和适用范围，不复述技能里的通用规则。项目的现有写法和技能规则不同又要沿用时，写进对应文件。

## 命令

```bash
node <skill-path>/scripts/project-memory.mjs init --project <path>
node <skill-path>/scripts/project-memory.mjs read --project <path> --file <path> --toc
node <skill-path>/scripts/project-memory.mjs read --project <path> --file <path> --section "<标题>"
node <skill-path>/scripts/project-memory.mjs index --write --project <path>
node <skill-path>/scripts/project-memory.mjs validate --project <path> [--format json]
```

| 命令 | 作用 |
| --- | --- |
| `init` | 从模板创建 `.project-memory/`（已经存在时不覆盖）；项目根目录没有 `AGENTS.md` 时一并创建，已有时不改动 |
| `read` | 按标题读一个章节，范围到下一个同级或更高级标题为止；`--toc` 列目录，`--full` 读全文。普通的 `rg`、`cat` 也可以读 |
| `index` | 列出目录过期的文件；加 `--write` 重建各文档的 `## 目录`，并按 front matter 重建 `INDEX.md` 的文档目录 |
| `validate` | 链接目标不存在、同一张表里编号重复、`id_high_water` 小于已用的最大编号、ADR 编号被多个文件占用时报失败；目录过期、锚点失效只给建议 |

初始化和修改记忆要在请求者同意的范围内进行。
