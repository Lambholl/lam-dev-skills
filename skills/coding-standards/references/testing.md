# 测试

写、改或删测试，或者决定要不要加测试时读。

## 长期测试测什么

长期自动化测试只覆盖稳定的边界：

- 接口的输入、输出、错误码和协议版本；
- 数据转换、持久化和文件读写；
- 难以手动重复的核心逻辑；
- 各平台实现不同、需要分别确认的基础行为。

界面不进长期测试：按钮、组件树、DOM 选择器、文案、弹窗、布局、样式和颜色靠实际运行检查。临时写的自动化检查确认完就删，不提交快照测试。稳定的逻辑只能通过界面触达时，把逻辑移到服务或状态模块，测那里的接口。

不设覆盖率目标。

## 什么时候新增

默认不新增、不扩写长期测试，维护者在当前任务里明确要求时才写。实现功能、修复 bug、重构和清理代码，都不等于要求写测试。

开发时可以临时测一个具体场景，确认后删掉临时断言。

提议新增长期测试或在项目记忆（如 `testing/coverage-gaps.md`）登记测试缺口前，必须先对照“长期测试测什么”和“留还是删”逐条筛查。以下情况不提议，也不登记为测试缺口：

- 已排入真机或人工验收的端到端主流程；
- 下层边界已有测试、且需要拼装大量假对象或模拟端才能串联的跨模块集成流程；
- 用假桩绕过真实核心逻辑的测试；
- 同类模块已接受不设长期测试的情况；
- 只为覆盖边缘场景的未测项。

只有确认属于稳定边界（如无真机验收覆盖的 CLI、脚本、数据转换或独立服务边界）且存在高风险回归时，才向维护者说明：风险是什么、要测哪些场景、预计多少行测试代码、现有检查为什么不够；维护者同意后再写。

## 留还是删

决定一条长期测试写不写、留不留时，按顺序回答：

1. 这条测试失败时，会不会导致数据丢失或写错、各自安装或升级的两端或新旧版本之间连不上或读不懂、安全边界被越过，或核心逻辑与公开契约静默出错？都不会就不写；已发布的落盘格式、备份和协议版本的读取与迁移是兼容面，优先保留。
2. 它是不是只在验证写代码时自定的取值（默认值、超时、间隔、无风险上限）？是就只测行为或规则本身，不测具体数值（如备份保留份数只测轮换时先删最旧的，不测具体保留几份或上限是多少）；超出后有风险的上限只测“上限生效”。
3. 只改实现、不改行为时，这条测试会不会失败（如依赖内部调用顺序、私有字段或日志文本）？会就改成测公开接口，改不了就删。
4. 同一条规则在别的层级或接口的另一侧已经测过吗？测过就删掉重复的一条。

以下几类直接不留、删除或合并：

- 界面和文案；
- 只影响显示的计算：进度百分比、计数汇总、显示顺序，写在纯逻辑模块里也一样（决定写入、删除或跳过哪些数据的逻辑照常测）；
- 同一构建内两部分之间的薄桥（界面和原生插件、宿主和随它一起发布的子进程）：参数和事件的原样转发、对另一部分返回格式的校验、“不在该平台上”的分支（外部输入校验只在执行检查的一侧测一次）；
- 随应用一起发布、启动时就会出错的内部消息解析；
- 第三方框架（含序列化框架）、语言或系统自身行为；
- 项目自己的开发工具和检查脚本；
- 需求变化后已经失效的用例。

测试失败时先判断是回归还是需求变了。需求变了就删掉旧断言，不为让测试通过而扩大测试范围。

## 测试写法

- 测试名写一个行为和结果，如“下载返回目标文件”。
- 一个用例只测一个场景，断言集中在公开接口的输出、错误和副作用上。
- 测公开边界，不依赖私有函数、内部调用次数和实现步骤。
- 只有来自协议、外部标准或产品需求的预期值可以断言字面量；代码自定的默认值、超时、间隔和有风险上限不写死字面量，断言引用常量。
- mock 只用来替代外部依赖、设备和需要人为制造的故障；内部代码直接执行。
- 类型约束由类型检查器保证，不写类型反例测试。
- 自动化测试只使用合成数据和系统临时目录，不读写或依赖真实用户数据。
