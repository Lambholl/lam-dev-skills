# 编码规范

## 项目差异

先读项目对编码和测试的约定：有 `.project-memory/` 时读 `.project-memory/standards/coding.md` 和 `testing.md`，没有时看 `AGENTS.md`、`CLAUDE.md` 里的相应内容。

优先级从高到低：

1. 请求者本轮的要求；
2. 项目的工具配置和代码事实：linter、formatter、类型检查、构建配置、`.editorconfig`、Schema、测试；
3. 项目约定；
4. 本技能；
5. 仓库现有风格。

工具配置和本技能冲突时以配置为准。现有风格和本技能不同又要沿用时，把差异和原因写进项目约定。

能由配置、lint、类型检查、Schema、测试或 CI 执行的规则，由工具检查；文档只写目标、范围、配置位置和例外。

## 读哪些文件

编写、修改或评审源码前，必须先读本文件、项目约定和对应的语言/框架规则；长会话发生上下文压缩后继续改代码时重读。

| 任务 | 读取 |
| --- | --- |
| 写、改或评审代码 | 本文件，以及 `references/languages/` 下目标文件语言的规则 |
| 写、改或评审 React（`.jsx`、`.tsx`）或 Vue（`.vue`）组件 | 另读 `references/frameworks/react.md` 或 `vue.md` |
| 写、改或删测试，或者决定要不要加测试 | 另读 `references/testing.md` |
| 配置 CI、lint、formatter、类型检查或分析器 | 另读 `references/static-checks.md` |

语言规则已有：TypeScript、JavaScript、Python、Java、C#、C、C++、Rust、Shell、PowerShell。没有专属文件的语言只用本文件。框架规则已有：React、Vue。

## 文件编码和换行

- 源码、Markdown、配置和工程文件用 UTF-8（无 BOM），换行用 LF。
- `.editorconfig` 声明 `charset = utf-8` 和默认换行；Git 仓库用 `.gitattributes` 把文本文件规范成 LF，只给 `.bat`、`.cmd` 声明 CRLF。
- 工具链要求 BOM 或 CRLF 的文件（旧式 `.csproj`、要兼容 Windows PowerShell 5.1 的脚本）在 `.editorconfig` 里单独声明，原因写进项目约定。
- GBK、Big5、Latin-1 等编码只出现在第三方代码和测试样本里，在文件旁或项目约定里写明原因。
- 不提交乱码、混合换行、不可见控制字符和意外的 BOM。

## 语言选择

- 新项目和新模块没有技术栈约束时，用 Python 或 JS/TS。
- Rust 只在请求者明确要求或维护已有 Rust 代码时用。
- PowerShell 只在操作注册表、只有 PowerShell cmdlet 能完成 Windows 系统管理，或维护已有 PowerShell 脚本时用；其他脚本用 Bash 或项目已有的脚本语言。

## 命名

- 名字说清是什么、做什么，用代码和项目术语表里查得到的词。
- 布尔变量、参数和字段用 `is`、`has`、`can`、`should`、`was`、`did`、`will`、`must`、`need`、`allow`、`support`、`contain`、`include`、`exist`、`match` 等前缀，大小写跟随语言，如 `isConnected`、`has_permission`。语言规则或框架规则另有约定的按它们的规则。

## 错误处理

- 错误在能处理的地方处理，处理不了就带着原因向上抛。不写空 `catch`；确实可以忽略的错误写明为什么能忽略。
- 包装错误时保留原始原因和上下文。跨模块、跨进程的边界用稳定的错误码或错误类型。
- 只给实际会出现的输入和状态写检查。不为假想的调用方、不可能的状态写分支和兜底：多余的分支让代码难读，兜底会把真正的错误吞掉。外部输入（用户输入、文件、网络、环境变量、命令行参数）在进入系统的地方校验一次。
- 日志不写密钥、令牌、个人隐私和未脱敏的客户数据。

## 注释

### 注释的语言

用项目约定的语言。项目没有约定时跟随同一文件和同一模块的现有注释；新项目没有可参照的代码时，用请求者在对话里用的语言。代码标识、API 名称、文档标签、工具识别的指令（如 `eslint-disable`、`# type: ignore`）和第三方许可声明保留原文。

下面的规则对所有语言的注释都适用。

### 文档注释

文档注释写在声明上，说明当前符号对外提供的行为（接口契约），让读者不读实现就能正确调用它、处理结果和错误。各语言的形式和标签见语言规则：TSDoc/JSDoc、docstring、Javadoc、XML documentation、rustdoc、Doxygen、comment-based help、Shell 函数头注释。

**哪些要写**

- 模块外可见的符号必须写：导出的函数、类、类型和常量，公共方法，CLI 和脚本入口，配置项，跨模块、跨进程和跨语言的接口。
- 模块内部的符号、字段和枚举成员，名字和类型已经说清楚时不写；有单位、取值范围、空值含义或状态语义时写。
- 声明和实现分开的语言（C/C++ 头文件）写在声明处，实现处不重复。

**写什么**

第一句是摘要：函数写做什么、作用于什么、返回什么；类型写它表示什么。摘要够用就只写这一句，否则按需补充：

| 内容 | 例子 |
| --- | --- |
| 输入约束：类型表达不了的单位、范围、格式、前置条件，以及不满足时的结果 | `deviceId` 必须已登记，否则抛 `NotFoundError` |
| 返回值的特殊含义 | 找不到时返回 `null` |
| 错误：抛出的异常或返回的错误码及触发条件；异步操作的完成、失败和取消 | 版本高于当前程序支持的版本时抛 `ConfigVersionError` |
| 副作用：修改入参、写文件、改全局状态、发事件或网络请求 | 原地排序 `entries` |
| 资源和并发：所有权、释放方式、线程安全、是否阻塞、回调的触发时机 | 返回的句柄由调用方关闭 |
| 兼容性：已发布的格式、协议或接口要保持的约束 | 字段顺序和 v1 文件格式一致 |

用肯定句写会发生什么，且必须与当前实现的全部公开分支、返回值和异常一致。类型已经表达的内容不重复；代码里已有常量或配置项时直接引用常量名，不在注释里重复写死数值。

**禁止写进文档注释的内容**

文档注释只写当前符号自己的对外契约，下面这些必须写在别处：

| 内容 | 写在哪里 |
| --- | --- |
| 调用方：谁调用、什么时候调用、哪个页面使用 | 调用前必须满足的条件写成输入约束，如“调用前必须先 `open`”；其余写在调用处的行内注释 |
| 实现：调用了哪些函数、分几步、内部心跳/重试周期、为什么这样做 | 实现代码旁的行内注释 |
| 没做的事与范围决定（如“断开后不自动重连”“不开机启动”） | 范围决定写进需求、约束或架构文档；维护者容易误补的刻意省略写在实现处的行内注释 |
| 版本演变与改动历史（如“5 起……”“不再……”） | Git 提交信息；文档注释只描述当前行为 |
| 所在进程、层或模块，模块之间的分工 | 项目架构文档 |
| 安全边界 | 项目架构文档，以及执行检查的代码旁 |

### 行内注释

行内注释写在实现代码旁，读者是要改这段代码的维护者。

- 写原因和后果，以及读代码看不出的内容：非显然的算法、平台和第三方库的特殊行为、一项检查防的是什么。
- 禁止复述代码。
- 禁止写代码没做的事和改动历史：没实现的功能、删掉的逻辑、别处已经规定的范围、版本演进。范围决定写进需求或架构文档，删除原因写进提交信息。
- 例外：维护者很可能顺手补上的刻意省略，在省略处写一句原因，如“这里不重试：写入不是幂等的”。

### 注释写法

- 写给第一次读这段代码的人：完整的句子，代码里查得到的名称，说清具体对象和触发条件。不用自造的简称和含糊指代（如“该期限”“原数据”），不用斜杠堆名词，不用分号挂否定分句。
- 代码里已有常量或配置项时，注释直接引用常量名（如 `PING_INTERVAL_MS`、`CLOSE_REPLACED`），不在注释里重复写死数值；只有协议/标准固定值（如 HTTP 403、RFC 关闭码）或无常量的外部约束才写具体数值。
- 术语在代码或项目术语表里查得到，同一个词只表示一种东西。
- 指代模块写类名或函数名，不按时间先后称呼（“新的那个解析器”）。禁止写工单号和项目记忆编号。
- 写给维护者，不写给评审者看的免责解释。限制是真实的，就写会发生什么，如“两次检查之间文件可能被替换”。
- 实现混乱时改命名、拆函数或调结构，不靠注释解释。

### 改已有注释

改文档注释时，按上面的规则把不属于契约的内容移走：实现细节移到行内注释，调用方信息改写成输入约束或移到调用处，架构说明移到项目文档。移走不算删除信息。架构文档里没有对应内容时，列出来问请求者。

 */

**改后（只写契约，引用常量名，内部机制移到实现处行内注释）：**

```ts
/**
 * 控制通道的监听端，同一时间维护一条设备连接。
 * 同一设备的新连接以 CLOSE_REPLACED 取代旧连接；心跳超过 PING_INTERVAL_MS 未响应时断开。
 */

```

  readonly deviceId: string

### 注释自检

批量改完源码后、报告完成或提交前，对照本次 `git diff` 里新增和修改的注释逐项核对，不靠写代码时的顺手记忆：

- **语言与覆盖**：是否使用项目约定的注释语言，新增的模块外可见符号是否都有文档注释？
- **准确性**：每条文档注释是否和当前实现的全部公开分支、返回值、异常一致，没有写漏或写反？
- **契约边界**：文档注释里有没有混入调用方（谁调用、哪个页面用）、内部实现步骤、所在进程/架构，或“不自动……/不开机……/不再……”这类没做的事与版本历史？
- **常量引用**：注释里出现的超时、上限、状态码等数值，代码里已有常量时是否已改成引用常量名？
- **行内注释**：是否只写原因、后果和非显然约束，没有复述代码、工单号或给评审者看的免责解释？

## 验证

按下面的顺序选验证方式，够用就停：

1. 格式、lint、类型检查、构建；
2. 实际运行程序，操作改动涉及的功能；
3. 和改动相关的最小一组已有测试；
4. 全量测试：只在发布前、大范围高风险改动后，或请求者要求时跑。

低风险的改动可以做完一批再统一验证；高风险的改动在关键步骤后立即验证。

验证结论只来自最后一次相关修改之后的运行结果。

## Hook

同一会话首次写入或修改源码时（以及上下文压缩后的首次源码写入），`PreToolUse` Hook 会拦下该次调用并提醒先读取本技能、语言规则和项目 `standards/coding.md`；读完后重试即可放行，同会话后续写入不再重复拦截。
